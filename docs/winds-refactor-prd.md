# Winds 重构需求文档

## 1. 背景

当前项目的业务内核已经明显偏向风机轴承诊断，但产品形态、命名方式和系统边界仍然沿用通用智能体项目的设计。

这导致两个直接问题：

1. 对用户而言，系统暴露的是 `Agent`、`知识库`、`聊天记录`、`模型参数`、`工具权限` 这些实现概念，而不是诊断任务、信号数据、参数卡、分析结果、诊断报告这些业务概念。
2. 对研发而言，系统表面上是通用 Agent 平台，内部却基本已经写死为风机轴承诊断工作流，架构抽象与真实业务边界不一致，后续扩展和维护成本会越来越高。

本次重构的目标不是在现有 UI 上继续修补，而是把项目重新定义为一个独立的风机轴承诊断产品，并据此重做产品信息架构和目标系统架构。

## 2. 当前问题判断

### 2.1 产品定位错位

- README 和主界面仍然在讲通用 AI Agent 能力。
- 前端主导航仍然是 `智能体助手`、`聊天记录`、`知识库`。
- 用户入口是“选择一个智能体开始聊天”，不是“创建一个诊断任务”。

结果是：用户进入系统后，先看到的是实现方式，而不是要完成的业务任务。

### 2.2 交互模型错位

- 当前主流程是对话式交互。
- 诊断结果、分析证据、过程状态都被包裹在聊天会话里。
- 上传 MAT 文件和参数知识与诊断任务之间缺少明确的任务编排关系。

结果是：系统更像“能做诊断的聊天助手”，而不是“面向诊断工作的专业工作台”。

### 2.3 业务对象混杂

当前至少混在一起的对象包括：

- 信号文件
- 转速文件
- 参数卡
- 诊断规则
- 诊断任务
- 诊断报告
- 聊天消息
- 智能体配置

这些对象目前被塞进 `知识库`、`聊天`、`Agent` 这几个概念里，业务边界不清晰。

### 2.4 架构抽象与实现不一致

- 后端仍保留通用 `Agent` 平台的控制器、实体和配置方式。
- 工作流工厂实际上已经固定返回 `WindTurbineBearingWorkflow`。
- `Agent` 实体仍然承载 `systemPrompt`、`model`、`allowedTools`、`allowedKbs`、`chatOptions` 等平台型配置。

结果是：系统同时承担了“通用平台”和“单一行业产品”两套职责，但两套职责都没有完整设计好。

### 2.5 产品体验不足

当前缺失的不是按钮数量，而是面向业务的体验设计：

- 没有明确的“新建诊断任务”入口
- 没有诊断任务列表、状态、负责人、更新时间等任务视图
- 没有结构化的证据面板和诊断结论面板
- 没有参数校验、数据配对、异常提示等专业工作流节点
- 没有把 AI 放在正确的位置上：AI 应该作为分析引擎和辅助解释器，而不是让用户先理解智能体系统

## 3. 重构后的产品定位

### 3.1 产品定义

`Winds` 应重新定义为：

**面向风机传动链振动分析与轴承故障诊断的智能诊断工作台**

它的核心不是“和 AI 对话”，而是帮助诊断工程师围绕真实数据完成：

- 数据导入
- 通道识别与配对
- 参数加载
- 自动分析
- 证据审阅
- 结论确认
- 报告生成

### 3.2 目标用户

第一阶段建议聚焦 3 类用户：

1. 诊断工程师
   - 负责导入信号、发起分析、审阅证据、确认结论、导出报告
2. 设备/运维工程师
   - 查看诊断结论、风险等级、建议动作，不一定参与全部分析过程
3. 知识管理员
   - 维护参数卡、经验规则、参考频率、分析模板

### 3.3 产品原则

1. 任务优先，不以聊天为中心
2. 领域对象优先，不暴露 AI 内部概念
3. 结构化结果优先，不把核心结果埋在对话记录中
4. 人机协同优先，AI 给出分析与证据，最终结论可人工确认
5. 可追溯优先，结论必须能回溯到信号、特征峰值、参数来源和规则依据

## 4. 重构目标

### 4.1 业务目标

重构后，用户应该能够在一个统一工作台中完成以下闭环：

1. 创建诊断任务
2. 关联振动/转速信号
3. 关联参数卡和规则
4. 运行诊断分析
5. 审阅分析证据
6. 输出结构化诊断报告

### 4.2 产品目标

重构后首页和主导航不再出现以下概念作为主入口：

- Agent
- 聊天记录
- 知识库
- 模型设置
- 工具权限

这些概念如确有保留价值，应退到后台配置层或管理员层，而不是普通用户主流程。

### 4.3 技术目标

重构后系统架构应符合以下原则：

1. 前后端模块以业务能力划分，而不是以通用 Agent 平台划分
2. AI 能力、RAG、工具调用属于内部能力层，不直接映射为用户主概念
3. 诊断任务、信号资产、知识参数、分析结果、报告是一级业务对象
4. 工作流编排应以诊断任务为中心，而不是以聊天会话为中心

## 5. 目标产品形态

### 5.1 一级导航建议

建议将产品主导航调整为以下结构：

1. 工作台
2. 诊断任务
3. 数据资产
4. 参数与知识
5. 报告中心
6. 系统配置

### 5.2 页面定义

#### 5.2.1 工作台

用于展示：

- 待处理任务
- 最近分析结果
- 高风险设备
- 最近导入的数据
- 常用模板或快捷入口

这是业务首页，不是聊天首页。

#### 5.2.2 诊断任务

这是产品核心模块，至少应支持：

- 新建任务
- 任务列表
- 任务状态筛选
- 查看任务详情
- 启动/重新运行分析
- 人工确认结论

任务详情页应包含：

- 基本信息
- 关联文件
- 参数上下文
- 分析进度
- 频谱/包络/转速/阶次等结果面板
- 证据摘要
- 诊断结论
- 报告导出

#### 5.2.3 数据资产

将现有“知识库里的文档上传”拆开，改为数据资产视角，至少区分：

- 振动信号文件
- 转速/测速信号文件
- 解析后的通道元数据
- 数据归属设备/机组/采集时间

这个模块负责的是“数据准备”，不是知识问答。

#### 5.2.4 参数与知识

建议拆分为两类资源：

1. 结构化参数
   - 参数卡
   - 轴系信息
   - 轴承几何参数
   - 通道映射
   - 推荐包络频段
2. 诊断知识
   - 故障机理说明
   - 规则阈值
   - 经验案例
   - 参考频率知识

参数类数据应优先结构化，不应长期仅依赖 Markdown 和 RAG 解析。

#### 5.2.5 报告中心

用于沉淀最终产出，包括：

- 已完成诊断报告
- 版本记录
- 结论修订记录
- 导出下载

报告是一级对象，不应只是聊天中的一段文本。

#### 5.2.6 系统配置

仅管理员可见，放置：

- 模型配置
- AI 策略
- 分析模板
- 阈值模板
- 知识源配置

这里才允许保留一部分当前 `Agent` 的能力，但需要重新命名和约束。

## 6. 核心用户流程

### 6.1 诊断工程师主流程

1. 新建诊断任务
2. 选择或上传振动文件
3. 选择或上传转速文件
4. 选择设备参数卡 / 机型参数模板
5. 系统自动识别通道、采样率、候选速度信号
6. 用户确认或修正映射关系
7. 系统执行基础分析与高级分析
8. 系统输出候选故障、关键证据、置信度、建议动作
9. 工程师审阅后确认诊断结论
10. 导出正式报告

### 6.2 数据管理员流程

1. 上传新的 MAT 文件或批量导入
2. 检查解析状态
3. 修正文件元数据
4. 维护参数模板和参考频率
5. 维护知识条目和规则阈值

### 6.3 运维用户流程

1. 查看任务结果
2. 关注风险等级和建议处理动作
3. 下载诊断报告
4. 查看历史同设备结果对比

## 7. 核心功能需求

### 7.1 任务管理

必须支持：

- 新建任务
- 草稿态 / 分析中 / 待确认 / 已完成 / 失败
- 任务关联设备、机组、时间、责任人
- 任务重跑
- 任务复制

### 7.2 数据导入与校验

必须支持：

- 上传 MAT 文件
- 识别振动通道和转速通道
- 展示采样率、单位、设备名、信号名
- 标记解析失败原因
- 多文件配对

建议新增：

- 通道预览
- 波形/频谱快速预览
- 自动命名规则
- 批量导入能力

### 7.3 参数管理

必须支持：

- 设备参数模板
- 轴承几何参数维护
- 轴系转速参数维护
- 推荐包络频段维护
- 通道映射维护

建议新增：

- 参数完整性校验
- 缺失参数提示
- 模板版本管理

### 7.4 自动分析

必须支持：

- 基础频谱分析
- 包络分析
- 转速分析
- 阶次分析
- 参考频率匹配
- 故障候选生成

建议输出结构化结果：

- 峰值列表
- 特征频率匹配列表
- 指标摘要
- 证据强度
- 结论置信度

### 7.5 诊断结论与报告

必须支持：

- 风险等级
- 故障部位
- 关键证据
- 诊断说明
- 建议动作
- 不确定性说明

建议支持：

- 人工编辑报告
- 审批/确认记录
- PDF/Markdown 导出
- 历史报告对比

### 7.6 AI 助手能力

AI 能力建议保留，但角色必须降级为辅助能力，而不是主产品壳。

建议保留为：

- 对分析结果做解释
- 对异常峰值做问答
- 对规则依据做说明
- 对报告做语言润色

不建议继续让终端用户直接配置：

- system prompt
- allowed tools
- allowed knowledge bases
- context compression
- runtime cache

这些应转为后台策略配置或彻底隐藏。

## 8. 非功能需求

### 8.1 可追溯

任一诊断结论都需要能追溯到：

- 原始文件
- 具体通道
- 关键频率
- 参数来源
- 规则来源
- AI 生成说明

### 8.2 可恢复

长任务分析应支持：

- 进度可视化
- 中断后状态恢复
- 失败原因记录
- 重新执行

### 8.3 可维护

后续增加新机型、新参数模板、新故障规则时，不应再改动通用聊天层代码。

### 8.4 可扩展

后续应能扩展到：

- 齿轮箱其它部件诊断
- 发电机部件诊断
- 更多设备模型
- 更多分析模板

## 9. 目标系统架构建议

### 9.1 总体原则

建议从“通用 Agent 平台”架构，重构为“领域驱动的诊断系统”架构。

推荐至少拆成以下业务模块：

1. `diagnosis-task`
   - 任务创建、状态流转、任务编排
2. `signal-asset`
   - 文件上传、解析、元数据、通道识别
3. `parameter-knowledge`
   - 参数模板、规则、参考频率、知识条目
4. `analysis-engine`
   - 频谱、包络、转速、阶次、特征匹配
5. `diagnosis-report`
   - 结构化结论、导出、版本管理
6. `ai-assistant`
   - 解释、总结、问答、语言生成

### 9.2 后端分层建议

建议后端采用以下分层：

- Interface 层
  - Controller / API DTO / SSE 接口
- Application 层
  - 任务编排、用例服务、权限编排
- Domain 层
  - 任务、报告、参数、规则、分析结果等核心模型与领域服务
- Infrastructure 层
  - 大模型、RAG、向量检索、文件存储、数据库、第三方工具

关键点：

- `WindTurbineBearingWorkflow` 应演进为面向诊断任务的应用服务或编排器
- 通用 `AgentWorkflowFactory` 不应继续作为系统核心抽象
- `Agent` 这类平台型实体应逐步退场，替换为 `分析模板`、`诊断策略`、`系统配置`

### 9.3 前端模块建议

前端建议按业务区域拆分，而不是按聊天/知识库拆分：

- `workbench`
- `diagnosis-tasks`
- `data-assets`
- `parameter-library`
- `reports`
- `settings`

每个模块内部再拆：

- 页面容器
- 领域组件
- 查询/命令 hooks
- API schema

### 9.4 数据模型重构建议

建议引入或强化以下一级实体：

- `DiagnosisTask`
- `SignalAsset`
- `SignalChannel`
- `ParameterTemplate`
- `DiagnosisRule`
- `AnalysisRun`
- `AnalysisEvidence`
- `DiagnosisReport`

同时逐步弱化以下概念在主业务中的地位：

- `Agent`
- `ChatSession`
- `ChatMessage`
- `KnowledgeBase` 作为统一容器

## 10. 版本规划建议

### Phase 1: 产品壳重构

目标：

- 改主导航和主页面
- 从聊天入口切换到任务入口
- 梳理新的业务对象命名

交付标准：

- 用户进入系统后，主流程已是“新建诊断任务”
- 不再要求用户先理解 Agent 才能使用系统

### Phase 2: 任务工作台重构

目标：

- 建立诊断任务详情页
- 把分析进度、证据、结论做成结构化面板
- 数据上传和任务关联打通

交付标准：

- 用户可以完整跑通“导入数据 -> 运行分析 -> 查看结构化结论”

### Phase 3: 参数与知识重构

目标：

- 把参数卡从纯 Markdown 依赖逐步转为结构化模板
- 建立规则和参考频率维护能力

交付标准：

- 参数完整性可校验
- 知识和参数职责分离

### Phase 4: 报告与闭环增强

目标：

- 完成报告中心
- 支持人工确认、修订记录、导出
- 增加历史结果对比和案例沉淀

交付标准：

- 报告成为独立一级对象
- 诊断闭环完整可追踪

## 11. 本轮重构范围建议

如果要控制风险，建议本轮重构先做以下范围：

1. 产品重命名和导航重构
2. 新建诊断任务主流程
3. 数据资产与知识参数拆分
4. 任务详情页结构化结果展示
5. 将聊天能力降级为辅助侧边栏或结果解释面板

不建议本轮一开始就做：

- 全量算法升级
- 复杂权限系统
- 多租户
- 大规模平台化抽象

先把“产品是否成立”做对，再谈平台化。

## 12. 成功标准

重构完成后，应该满足以下判断标准：

1. 新用户不需要理解 Agent、Prompt、Tool 才能发起诊断
2. 一个诊断任务可以独立承载数据、参数、分析、证据和报告
3. 核心结果不依赖聊天记录作为唯一载体
4. 后端业务模块命名能直接对应产品模块
5. 后续新增机型或规则时，改的是参数/规则/模板，不是聊天壳代码

## 13. 当前代码与目标之间的关键改造点

1. 前端入口从 `AgentChatView` 迁移到 `DiagnosisTask` 视角
2. `KnowledgeBaseView` 拆分为 `数据资产` 与 `参数/知识`
3. `AddAgentModal` 所承载的大量用户配置下沉到后台策略层
4. `ChatSession` 从主业务容器退化为辅助交互记录
5. `AgentWorkflowFactory` 和 `WindTurbineBearingWorkflow` 迁移为任务编排服务
6. 诊断报告从聊天文本升级为结构化报告对象

## 14. 待确认问题

以下问题需要在进入详细设计前确认：

1. 第一阶段产品是面向内部诊断专家，还是也要面向非专家运维人员
2. 任务是否需要多人协作、审核、审批
3. 参数卡是否有稳定来源，能否直接建设结构化模板
4. 报告最终输出格式以页面、Markdown 还是 PDF 为主
5. 当前是否需要支持多机型、多部件，而不仅是风机轴承
